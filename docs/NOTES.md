# Build notes

## Locked decision: a "day" is the daily prompt's date

Streaks are counted in UTC calendar days, and that is the same unit as the prompt
of the day. When the prompt rolls over, the day rolls over, for everyone at once.

This was a deliberate trade. The "correct" alternative is a per-user local
midnight, so someone practicing at 8pm gets credited to their own today. It was
rejected because it lets a user's streak and their daily prompt disagree about
what day it is — you can be shown today's new prompt while your streak still
thinks it's yesterday, and the bug reports that follow are unfalsifiable. One
shared clock is easier to reason about and easier to explain in the UI.

The cost is real and accepted: a user in UTC+13 has a day boundary in the middle
of their afternoon. Revisit only with a concrete complaint, and if it changes,
`lib/streaks.ts` is the only place that decides — everything else takes a day key.

## Streak state is stored, not derived

`users/{uid}` holds `currentStreak`, `longestStreak`, `lastPracticeDay`, and
`daysPracticed`, updated transactionally when a session is recorded.

Deriving the streak by scanning a user's sessions was the obvious alternative and
is wrong: the read cost grows with the most engaged users, which is exactly the
wrong direction. The tradeoff is that stored state goes stale — a user who last
practiced three days ago still has `currentStreak: 5` on disk. Display therefore
goes through `visibleStreak()`, which returns 0 once a full day was missed. Never
render `currentStreak` directly.

## Removed: the custom Python ML scoring model

An earlier iteration added a Python workspace that trained a gradient-boosting
model on engineered transcript features to predict the four dimension scores,
served over a FastAPI endpoint the Next.js route called.

It was removed. The only labels available to train it were generated by an LLM
teacher, so the best the model could do was imitate the system it was meant to
replace — while adding a second runtime to deploy, version, and keep in sync
with the rubric. The engineered features were the genuinely useful part, so they
now live in `lib/scoring/metrics.ts` and are computed in-process and handed to
the model as evidence — and, since scoring v2, used to constrain what it returns.

Worth revisiting only with real human-labeled sessions to train against. Until
then, scoring stays with the LLM against a written rubric.

## Locked decision: `/practice` must match the landing page mockup exactly

The recorder preview in `components/marketing/RecorderMockup.tsx` is the
canonical design for the real `/practice` interface. When building the live
recorder, treat that mockup as the spec — same layout, spacing, type scale, and
component order — not as loose inspiration.

Required parity:

- Header row: `Day {n}` + category on the left, `{n} day streak 🔥` badge on the right
- `TODAY'S CHALLENGE` label above the prompt, same uppercase tracking treatment
- Prompt in the same size/weight/measure
- Circular ember mic button, same diameter, with the expanding ring on record
- Monospace tabular timer counting `01:00` down to `00:00`
- Waveform directly beneath the timer, same bar width/gap/height envelope
- Footer row with `Cancel` and `Finish →`

Differences allowed only where interaction demands it: the waveform must be
driven by real mic amplitude via `AnalyserNode` instead of the fixed amplitude
array, the timer must actually count down and auto-stop at zero, and the mic
button/controls change with the `ready | recording | processing` state.

Ideally `RecorderMockup` and the live recorder share the same presentational
subcomponents so the two can never drift apart.
